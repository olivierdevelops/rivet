# 10 · UI — dumb views, all logic in the handler

[← Codebase intelligence](09-intelligence.md) · [wiki index](README.md)

Every way the outside world reaches the program is a **surface**, and every surface splits into exactly two
parts: a **view** that only renders, and a **handler/controller** that holds all the logic. This page is the
UI-shaped statement of the rule the rest of the wiki states structurally — it applies identically to a mobile
screen, a desktop window, a web page, an HTTP route, a CLI command, and a socket message.

**The rule in one line:** the view turns *state into pixels* and *gestures into events*, and does nothing
else; the controller turns *events into a call on a feature port* and *results into state*; the use case
behind the port never learns that a UI exists.

---

## 1 · Where UI lives in the five folders

```
   ┌───────────────────────────── io/<surface>/ ──────────────────────────────────┐
   │                                                                              │
   │   VIEW  (dumb)                       CONTROLLER / ViewModel  (all logic)     │
   │   ┌────────────────────────┐         ┌───────────────────────────────────┐   │
   │   │ widgets · layout       │ event → │ state machine                     │   │
   │   │ state → pixels         │         │ input validation                  │   │
   │   │ gesture → event        │ ←state  │ calls the feature protocol        │   │
   │   │ no domain decisions    │         │ result → view state / error copy  │   │
   │   └────────────────────────┘         └────────────────┬──────────────────┘   │
   │                                                       │ depends on           │
   │                              login_feature.py ◄───────┘                      │
   │                              (declared in io/, next to the controller)       │
   └───────────────────────────────────────────┬──────────────────────────────────┘
                                               │ satisfied by
                        ┌──────────────────────▼───────────────────────┐
                        │ orchestrator/setup_<surface> — wiring only   │
                        └──────────────────────┬───────────────────────┘
                                               ▼
                        features/<feature>/  pure use case  ──needs──►  ports
                                                                          │
                                                            infra/ adapters satisfy them
```

Three facts follow from the picture, and `validate` enforces the structural ones:

- **`io/` may import only `domain/`.** A view or controller can never import a feature, another surface, or
  an adapter. The protocol the controller needs (`LoginFeature`) is declared **in `io/<surface>/`, next to
  the controller that uses it** — the orchestrator injects something that satisfies it.
- **Registration is per surface.** `mobile`, `desktop`, `web` and `cli` are four surfaces, so four
  `orchestrator/setup_<surface>` files. Missing one is `IssueMissingSetup`.
- **The use case is surface-blind.** It has no `vhco:trigger`, no notion of a screen, and cannot tell a tap
  from a `curl`.

---

## 2 · The same split, on every surface

The GUI vocabulary ("view", "ViewModel") is just the most familiar naming. Every `io/` surface has the same
two halves:

| Surface | The **dumb** half | The **logic** half | Event that enters | Rendered output |
|---|---|---|---|---|
| Mobile app | Screen / composable / widget tree | ViewModel · Presenter · Store | tap, swipe, long-press | pixels |
| Desktop app | Window / view / QWidget | ViewModel · Presenter | click, menu item, shortcut | pixels |
| Web (SPA) | Component / template | Controller · hook · store | click, submit, route change | DOM |
| Web (server-rendered) | Template / partial | Route handler | HTTP request | HTML |
| HTTP API | Response serializer | Route controller / handler | HTTP request | JSON |
| CLI | Output formatter / printer | Command handler | argv + stdin | stdout / exit code |
| WebSocket | Message serializer | Message controller | inbound frame | outbound frame |
| TUI | Screen painter | Controller | keypress | terminal cells |

If a rule below says "the view", read it as "the dumb half of your surface". A CLI printer that decides
*whether the operation should have run* is exactly as wrong as a button that validates an email address.

## 3 · What "dumb" precisely means

A dumb view is **allowed** to branch — on the state it was handed. It is **not** allowed to derive that state
itself. The distinction is the whole rule:

```
   ALLOWED                                   BANNED
   ───────────────────────────────────────   ─────────────────────────────────────────
   switch on a state enum the controller     computing which state we're in from raw
   produced  (LOADING → spinner)             data  (if len(items) == 0 and not error…)

   show a message the controller chose       deciding a domain rule
   (result.error_text)                       ("@" in email, price > 0, role == admin)

   emit an event  (on_sign_in_pressed)       calling a use case, a port, or an adapter
                                             directly

   pure formatting/layout of given values    fetching, caching, retrying, persisting
```

| The view may | The view may **not** |
|---|---|
| Bind fields of a view state to widgets | Read or write a store, file, socket, clock |
| `switch`/`if` on a **state enum** it was given | Compute that enum from domain data |
| Call `controller.on_x(...)` with raw input | Call a feature, port, or infra adapter |
| Format for display (dates, currency, plurals) | Validate, sanitize, or transform meaning |
| Own animation, focus, scroll position | Own retries, debounce policy, pagination logic |
| Take **one** dependency: its controller | Take callbacks/lambdas as constructor params |

> **Why "no callbacks as parameters".** A view that accepts `on_sign_in` as a parameter has no declared
> counterpart — nothing in the model says which controller it belongs to, and the wiring becomes ad-hoc at
> each call site. A view depends on **its controller**, one object with a named protocol, so the edge is
> visible in the model and reproducible in tests.

### Handlers / Views — respond or render only

```python
# io/login/login_handler.py  (HTTP example)

def handle_login(request, controller):
    result = controller.on_sign_in(request.email, request.password)
    if result.state == LoginState.SUCCESS:
        return Response(200, {"token": result.token})
    elif result.state == LoginState.INVALID_CREDENTIALS:
        return Response(401, {"error": "Email or password is incorrect."})
    elif result.state == LoginState.NETWORK_UNAVAILABLE:
        return Response(503, {"error": "Service temporarily unavailable."})
```

Every branch here is on a **state the controller produced** — the handler adds only the transport-specific
shell (status codes). That is the legal kind of branching.

```python
# ❌ Wrong — business logic in the handler
def handle_login(request, on_sign_in):   # ❌ no callbacks as parameters
    if "@" in request.email:             # ❌ business logic in handler
        on_sign_in(request.email, request.password)
```

## 4 · ViewModels / Controllers — logic only

The controller or ViewModel declares the feature protocol it needs. This protocol lives in `io/`, next to the
controller that uses it.

```python
# io/login/login_feature.py — controller declares the protocol it needs
class LoginFeature(ABC):
    def login(self, email: str, password: str) -> Result: ...

class LoginError(Enum):
    INVALID_CREDENTIALS = "invalid_credentials"
    NETWORK_UNAVAILABLE = "network_unavailable"
    UNKNOWN = "unknown"

class LoginState(Enum):
    IDLE = "idle"
    LOADING = "loading"
    SUCCESS = "success"
    ERROR = "error"
```

```python
# io/login/login_controller.py
class LoginController:
    def __init__(self, feature: LoginFeature):
        self._feature = feature
        self.state = LoginState.IDLE
        self.token = None

    def on_sign_in(self, email: str, password: str) -> LoginResult:
        self.state = LoginState.LOADING
        result = self._feature.login(email, password)
        if result.ok:
            self.state = LoginState.SUCCESS
            self.token = result.token
        else:
            self.state = LoginState.ERROR
            self.error = result.error
        return self
```

`LoginFeature` is declared in `io/login/` — next to the controller that uses it. The orchestrator injects
something that satisfies it.

### The controller owns exactly this

```
        ┌──────────────────────── LoginController ────────────────────────┐
        │  1. input validation      "email is blank" → ERROR, no call     │
        │  2. state machine         IDLE → LOADING → SUCCESS | ERROR      │
        │  3. one call out          self._feature.login(...)              │
        │  4. result → view state   Result{ok,token,error} → LoginState   │
        │  5. presentation policy   which message, which screen next      │
        └─────────────────────────────────────────────────────────────────┘
                    it does NOT: touch a DB, build a widget, know a route
```

The state machine is the controller's real product — the view is a pure function of it:

```
            on_sign_in                 feature.login ok
   ┌──────┐ ─────────► ┌─────────┐ ───────────────────► ┌─────────┐
   │ IDLE │            │ LOADING │                      │ SUCCESS │
   └──────┘            └─────────┘ ───────────────────► └─────────┘
      ▲                              feature.login err        │
      │                                    │                  │ navigate
      │                                    ▼                  ▼
      │      on_retry / on_dismiss   ┌───────┐          (next screen)
      └────────────────────────────  │ ERROR │
                                     └───────┘
   view render:  IDLE→form · LOADING→spinner+disabled · ERROR→form+banner · SUCCESS→route away
```

## 5 · One controller, many shells

Because the controller holds the logic and the view holds none, the *same* controller drives every platform
shell. This is the payoff, and it is why the split is not ceremony:

```
     io/mobile/          io/desktop/          io/web/
   ┌────────────┐      ┌────────────┐      ┌────────────┐
   │ LoginScreen│      │ LoginWindow│      │ <LoginForm>│     ← dumb, platform-specific
   └─────┬──────┘      └─────┬──────┘      └─────┬──────┘
         │ events/state      │                   │
         └───────────────────┼───────────────────┘
                             ▼
                    ┌──────────────────┐
                    │ LoginController  │                       ← logic, platform-free,
                    │  + LoginFeature  │                         testable with no toolkit
                    └────────┬─────────┘
                             │ injected in each setup_<surface>
                             ▼
                 features/auth/login  (pure use case)
                             │ needs
                             ▼
                 CredentialStore · SessionClient   ← ports, satisfied by infra/
```

Each shell still needs its own registration file, and each lists the actions it routes:

```go
// orchestrator/setup_mobile.go
// vhco:surface mobile  kind screen calls auth/login, auth/logout
// vhco:trigger mobile auth/login = tap "Sign in" on the Login screen

// orchestrator/setup_desktop.go
// vhco:surface desktop kind desktop calls auth/login, auth/logout

// orchestrator/setup_web.go
// vhco:surface web     kind http   calls auth/login
```

One use case (`auth/login`), three surfaces, zero duplicated logic. If two shells genuinely need different
*behavior*, that difference is a different controller or a different use case — never an `if platform ==`
inside a view.

## 6 · Making the UI legible: `screen` + `tap`

Structure alone doesn't tell a non-developer how the app is used. Two descriptive annotations do, and they
live where the UI actually is — on the view:

```kotlin
// io/mobile/task_detail_screen.kt

// vhco:screen task_detail route /tasks/:id via Home > Tasks > tap a task -- Task detail
class TaskDetailScreen(private val controller: TaskDetailController) {

    // vhco:tap task/delete_task @task_detail swipe at the top-right trash icon -- Delete this task
    fun onTrashSwiped() = controller.onDelete()
}
```

### Exact grammar

```
<comment> vhco:screen <id> [route <path>] [via <plain path…>]                 -- <title>
<comment> vhco:tap    <feature/action> [@<screen>] [<gesture>] [at <placement…>] -- <label>
```

- **`screen`** — `<id>` is the first token; `route` is the technical path (`/tasks/:id`); `via` is the
  **human** breadcrumb, rendered `Home › Tasks › tap a task`; the ` -- ` note is the screen's title.
- **`tap`** — `<feature/action>` normalizes to `feature.action` exactly like `usecase`/`calls`.
  `@<screen>` overrides the enclosing `vhco:screen` (which is the default, so you usually omit it).
  `at <placement…>` consumes the rest of the line, so put it **last**. The ` -- ` note is the label a
  human reads.
- **`<gesture>` is a closed vocabulary** — `tap` `press` `long-press` `swipe` `submit` `navigate`
  `toggle` `select` `drag` `scroll` `hold`. Anything else is not recognised as a gesture, and the
  gesture defaults to `tap`.

Both are recorded with `file:line`, so `vhco doc`/`vhco live` render a **Screens** view and a human-first
journey per use case:

```
   SCREENS                                        JOURNEY · task/delete_task
   ─────────────────────────────────────────      ────────────────────────────────────────
   Task detail          /tasks/:id                "Delete this task"
     Home › Tasks › tap a task                      swipe · on Task detail
     ├─ Delete this task   → task/delete_task       at the top-right trash icon
     └─ Rename             → task/rename_task       Home › Tasks › tap a task
                                                    ↳ io/mobile/task_detail_screen.kt:11
```

Note the split of responsibility with `vhco:trigger`: **`trigger` is the orchestrator's statement** ("this
surface routes this action"), while **`screen`/`tap` are the view's statement** ("this is where a human
touches it"). Both are descriptive — neither affects `validate`/`sync` — but a `trigger` naming an action
that isn't in that surface's `calls` *is* a `validate` finding.

## 7 · Testing follows the split

```
   VIEW           nothing to unit-test — it has no decisions.
                  (snapshot/render checks are optional and are about pixels, not logic.)

   CONTROLLER     the real test surface. Pass a fake LoginFeature; assert the state machine.
                  No UI toolkit, no emulator, no HTTP client, no DB.

   USE CASE       tested with fake ports — it never knew a UI existed.
```

The `vhco:test` subject is free text; naming the `feature.use_case` it exercises is what links the test back
to that use case in the explorer's **Tests** view — so a controller test names the action behind the
protocol, not the controller class.

```python
# tests/io/login/test_login_controller.py
# vhco:test auth.login -- the login controller reports ERROR when the feature rejects the credentials

def test_invalid_credentials_moves_to_error():
    controller = LoginController(FakeLoginFeature(ok=False, error=LoginError.INVALID_CREDENTIALS))
    result = controller.on_sign_in("a@b.c", "wrong")
    assert result.state == LoginState.ERROR
    assert result.error == LoginError.INVALID_CREDENTIALS
```

If a behavior can only be tested by driving a real screen, the logic is in the wrong half — move it into the
controller and the test becomes three lines with no device attached.

## 8 · Gotchas

- **The "just one `if`" in a view.** `if user.role == "admin": showDeleteButton()` is a domain decision in a
  widget. The controller exposes `state.can_delete` and the view binds to it.
- **Fetching in the view's lifecycle hook.** `onMounted → api.get(...)` skips the controller and the port
  entirely. The hook calls `controller.on_appear()`; the controller calls the feature protocol.
- **Callbacks as view parameters.** A view takes exactly one dependency — its controller. Loose lambdas
  make the surface→action edge invisible to the model.
- **A view importing a feature or an adapter.** `io/` imports only `domain/`. If a view needs something a
  feature knows, it goes through the controller's protocol, injected by `orchestrator/setup_<surface>`.
- **Platform `if`s inside one view.** `if (isMobile)` inside a shared component recreates two views badly.
  Two shells, one controller.
- **Formatting vs deciding.** Rendering `1699999200` as "2 days ago" is formatting (fine). Deciding an item
  is "stale" because it is older than two days is a rule (controller, or the use case).
- **Logic sliding into `setup_<surface>`.** Wiring a view to a controller is glue; choosing *which*
  controller based on data is a decision — push the fact into `infra`, the policy into a feature. See
  [Architecture](03-architecture.md).
- **Writing a `vhco:`-looking sentence in view prose.** The scanner parses it; keep prose comments clear of
  the directive shape.

## 9 · FAQ

**Q. Is a `switch` in a view allowed?** Yes, when it switches on a **state value the controller produced**.
No, when the view computes that value from domain data.

**Q. Where does input validation live?** Presentation-level checks ("this field is blank", "these two
passwords differ") belong to the controller. Rules that are true regardless of the UI ("a password must be
≥ 12 characters", "an order needs at least one line") belong to the use case, and the controller renders
whatever it returns.

**Q. Where does navigation live?** The controller decides *that* we move on (a `SUCCESS` state, or an
explicit `next_screen`); the view performs the platform-specific transition.

**Q. Mobile + desktop + web — one surface or three?** Three, when they have separate shells: three
`io/<surface>/` folders and three `orchestrator/setup_<surface>` files, sharing controllers where the
behavior is identical. One surface only if a single shell literally serves them all.

**Q. Is the ViewModel the controller?** Yes — same role, different community's word. The table in §2 maps
every surface's naming onto the same two halves.

**Q. My framework insists on state inside the component (hooks, signals, `@State`).** Keep it to *view*
state — focus, scroll, animation, expanded/collapsed. Application state stays in the controller, and the
component subscribes to it.

**Q. Do `screen`/`tap` change validation?** No. They are descriptive and only feed `vhco doc`/`vhco live`.
`vhco:trigger` is the one that must match a surface's `calls`.
